The current repo is a TypeScript DOM PWA with `src/app/main.ts`, `src/domain/models.ts`, `src/domain/validation.ts`, `src/data/db.ts`, `src/data/backup.ts`, reusable `src/ui/`, global `styles.css`, and a static PWA app shell. `npm test` compiles the app and runs Node tests. Live iPhone validations are distinct from these automated checks.

### Actual baseline to preserve

- App v0.1.0, IndexedDB DB `careerproof-local`, schema version **1**, object stores **profiles**, **achievements**, **meta**.
- Profile uses stable `local-profile` ID; persisted strings displayName/headline/summary/email/location, creation/update timestamps, revision.
- Achievements have stable IDs, title, contribution, exact-day `occurredOn`, draft/recorded/archived state, `preArchiveStatus`, outcome, `impactCategory`, timestamps and revision.
- JSON backup **format 1** contains exactly one profile and achievements with schema 1. Current `validateBackup` explicitly rejects mismatched schema/format versions; this is a **compatibility risk** if v0.1.1 changes the DB version.
- IndexedDB edit and delete repository methods check optimistic record revisions; keep these safeguards.
- Existing modal action routing fix and balanced mobile navigation must survive new forms/screens.

## 4. Highest-risk contracts and constraints

### 4.1 Database v1 migration
- Existing IndexedDB is named `careerproof-local`; current schema version 1, backup format 1.
- New object stores and indexes should be created in an additive migration where possible. Choose a direct v1→v2 path that preserves profile/achievement contents.
- The legacy achievement uses `occurredOn: "YYYY-MM-DD"`; the planned model introduces `occurredStart: PrecisionDate`. Either maintain a documented adapter or transactionally upgrade entries with an exact-day precision value; **never silently substitute a new date**. Track `occurredOn` compatibility while existing UI and v1 backups remain supported.
- Avoid IndexedDB transaction inactivity caused by unrelated awaited promises inside a live readwrite transaction.
- Close database connections on `versionchange`; handle blocked upgrades with a clear user recovery instruction.
- No indexedDB.deleteDatabase/reinitialize strategy; no transparent backup reset.

### 4.2 Backup round-trip and downgrade expectations
- Accept *both* a valid original v0.1.0 backup and a new v0.1.1 full backup after upgrade.
- Exports from new schema use a clearly versioned manifest; old format 1 is converted in memory, with new collections initialized safely.
- Restore validates all relationships and counts before opening a destructive transaction. If validation or write fails, preserve current records.
- Restoring a **legacy** backup to v0.1.1 is an explicit **full replacement** with no newly introduced record collections retained; preview this consequence clearly.
- A future/downgraded older v0.1.0 application is not required to read new backups.
- Maintain the warning that downloaded JSON is unencrypted and device-local data is not synced.

### 4.3 Relationship and privacy integrity
- Employer → Roles (1:N). Role→Achievement primary ID optional. Role↔Project, Project↔Achievement, Competency↔Achievement via valid typed `recordLinks`.
- Enforce unique typed links, valid endpoints and at most one primary project per achievement.
- Deleting an employer with roles blocks pending deliberate reassignment/removal. Removing a role may unlink/reassign achievements but must not erase them. Removing a project must retain achievements.
- Archiving an achievement must preserve its evidence and links. Permanent delete requires confirmation and safe removal of only directly dependent metrics/references/links.
- Store `confidentiality` as a first-class field, private by default; never publish actual project data in the repository or tests.
- Evidence references are user-entered descriptions/URLs/document IDs, **not** independent verification and not uploaded proprietary documents.

### 4.4 UI and PWA regression rules
- Keep `resolveActionTarget` behavior: clicks on modal inputs/selects/labels do not dismiss dialogs; direct backdrop clicks can close subject to unsaved-change confirmation.
- Preserve five equal-position items in the bottom mobile navigation currently composed of Home, Vault, Capture, Profile and Settings. When Growth is first functional, reorganize navigation deliberately to maintain spacing. Studio remains hidden until a real Studio feature ships.
- Retain layout at 320/375px, iPhone safe-area insets, and readable form fields with no overlays or bottom-bar overlap.
- Service-worker compiled-module pre-cache must update whenever `src/` adds ES modules.
- Generated output targets GitHub Pages `dist/` via CI; do not reconfigure Pages back to root deployment.

## 5. Test and release-acceptance criteria

### Must automate or demonstrate in a repeatable fixture
1. Seed realistic **synthetic** schema-v1 profile and multiple achievement statuses; upgrade; compare original IDs, contents, dates, timestamps and revisions to lossless migrated equivalents.
2. Define and validate historical PrecisionDate rules (year/month/day), including impossible dates and overlapping roles.
3. Create, edit and remove employers/roles/education/credentials without incorrect cascades.
4. Create two projects, one with several roles; link one achievement to more than one project, verify exactly one primary project.
5. Create, link and unlink multiple competencies, including custom skills; IDs remain stable after reload.
6. Create typed impact metrics and evidence references; reject invalid units, orphan references and duplicate relationships.
7. Archive/restore achievement; links and metrics survive.
8. Export full new backup → delete/change test records → restore → compare all counts and relationships.
9. Import legacy v0.1.0 backup into updated app; preserve old profile and achievement records and initialize missing collections.
10. Malformed/out-of-date/newer-unsupported backup rejected without changing any current data.
11. Hotfix regression: typing into dialogs never dismisses; bottom nav remains aligned; inputs not hidden behind keyboard.
12. Offline PWA: every compiled JS module and asset required at start is cached, and previously stored records load offline.

### Requires user/device verification after merge
- iPhone Safari (browser and preferably installed PWA): add/edit employer, role, project, achievement, and competency links.
- Confirm local records survive reload, cold restart and nav transitions.
- Verify no modal backdrop leakage, clipped forms or crooked mobile nav.
- Export backup in iOS Files; use **synthetic test data** for restore validation.
- Confirm offline open if test environment permits.
- Verify errors and dependent-record delete confirmations.

### Release acceptance gate
- `npm test` / typecheck / production build pass.
- Migration + backup integrity/regression tests pass.
- No unresolved critical data loss, privacy leak or broken link.
- Update docs/status/release notes in feature PRs, preserve compatibility.
- User reviews and merges each PR; actual phone UAT required before release deemed accepted.
